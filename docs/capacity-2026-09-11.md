# Capacity and live-history qualification — 2026-09-11

The bounded-storage cleanup initially reduced verified end-to-end throughput by
14–42% on this native Wait workload. Fusing live-cell/page hashing, reusing stable
leaf-map allocations, and skipping redundant membership lookups/page inserts
reduced the measured gap to 5.5–6.5% in the final rerun. The remaining cost is recorded, not treated
as a throughput improvement over the old dense storage.

## Dense-population comparison

Both builds use the same benchmark source, Rust 1.95.0, fixed seed 7, four Rayon
threads and four native Wait Minds. Digestion, metabolism, signal decay and
diffusion rates are disabled; the host maintains its ordinary projected view.
Each timed case completes two million actions, including observation, private
randomness, Mind calls, commitment, resolution, selected hash policy, deltas and
host projection. Setup and an added final independent canonical-hash/live-count
audit are outside the timer. This is an event-capacity workload, not active
physics, learned-policy inference, guest-WASM execution or ecological gameplay.

Baseline: revision `6dd66718d03507108d38844b623563a6f82fbfe0`, archived locally,
with only the identical benchmark audit/batch-count support added. Current is
the uncommitted cleanup tree with the final dense hash refresh changes. Runs are
serial fresh processes, alternating version order, with one warm-up and three
measured repetitions per version/case. All 64 runs agree on final canonical
hashes, committed/completed counts, live counts and key histories across builds
and both integrity modes.

### Rejected traversal-cache trial

A later immutable-page reader prototype avoided repeated directory lookup in
`CellIter`/`CellRange`. Range, reverse/mixed-end, sparse-key and held-reference
checks passed, but a 48-run comparison against a fresh pre-trial cleanup build
did not establish a useful gain. One warmup and five measured repetitions per
version/profile gave +0.69%/-1.51% verified and -0.45%/-1.52% on-demand throughput
on 128×128/2,000-cell and 512×512/50,000-cell profiles respectively. Every final
hash/count agreed. The prototype was reverted exactly; candidate sources, copied
binaries and raw timings remain under `training-output/page-cursor-2026-09-11`.
These comparisons use the cleanup as baseline, not the original repository base.

## Hash-refresh contract

Dense refresh enumerates only live pages, joins each page's ordered cells and
private-memory commitments, and computes leaf/page hashes together. It retains
map allocations when the complete live-key set matches; equal-length churn
falls back to rebuilding membership. Pending private-memory edits are always
applied. Already-computed page hashes are reused, while previously live pages
that became empty are still explicitly cleared. Cached historical subtrees and
monotonic-birth behavior remain intact; formats and simulation rules do not change.

Regressions cover stable entry addresses, serial/parallel and sparse pages,
equal-count deaths/births with pending memory changes, empty populations and
full canonical hashes after historical gaps. Final workspace tests pass 604
cases (33 ignored), workspace and engine/web WASM Clippy pass, and all eight
shared fuzz-harness tests pass. A fresh 300-second resolver sanitizer run passed
34,510 inputs without a finding. Browser package/fixture regeneration and the
real Chromium verification suite are also checked after the hash change.

## Historical-key resource comparison

The separate `lifetime_capacity` example constructs eight live cells with keys
spread across a specified historical key space, then measures cold canonical
restore plus first hash and subsequent verified Wait events. Idle and active
metabolism profiles are compared under identical canonical fixtures. These
fixtures model states after churn; they do not time generating that history,
execute Minds, or include a live server. The runner checks both initial and
final hashes against the baseline and measures peak RSS per process.

All 64 runs matched initial/final hashes and preserved eight live cells. Each
case has one warm-up and three measured runs per build with alternating order.
Active metabolism uses rate 1/1,024; the cells start with enough energy to remain
alive. Digestion, signal decay and diffusion are disabled. The table reports
medians; step times cover the stated number of complete verified batches.

| Historical keys | Metabolism | Batches | Restore ms, baseline/current | Events ms, baseline/current | Peak MiB, baseline/current |
| ---: | --- | ---: | ---: | ---: | ---: |
| 8 | idle | 1,000 | 0.028 / 0.026 | 8.545 / 8.109 | 2.27 / 2.25 |
| 8 | active | 100 | 0.032 / 0.025 | 1.292 / 1.340 | 2.44 / 2.48 |
| 65,536 | idle | 1,000 | 0.436 / 0.063 | 44.421 / 40.786 | 7.73 / 2.56 |
| 65,536 | active | 100 | 0.521 / 0.082 | 10.266 / 4.770 | 7.89 / 2.67 |
| 1,048,576 | idle | 1,000 | 6.422 / 0.730 | 52.418 / 48.845 | 85.75 / 2.95 |
| 1,048,576 | active | 100 | 6.900 / 0.775 | 83.247 / 5.222 | 86.14 / 3.11 |
| 4,000,000 | idle | 1,000 | 25.146 / 2.792 | 55.647 / 52.992 | 317.91 / 4.06 |
| 4,000,000 | active | 100 | 24.911 / 2.775 | 360.272 / 5.709 | 319.55 / 4.22 |

At four million historical keys with active metabolism, peak RSS falls from
319.55 to 4.22 MiB and 100 batches fall from 360.27 to 5.71 ms. Cold restore is
about nine times faster in that case. This measures the combined storage and
hash-history cleanup, not just the final dense-refresh optimization. Cold
restore still hashes historical empty pages, so its remaining O(history) cost
and the checkpoint key-space guard remain relevant. The result does not establish
throughput for a changing population, guest execution, or a complete online match.

```sh
cargo build --release --locked -p blob_engine --example lifetime_capacity
RAYON_NUM_THREADS=4 target/release/examples/lifetime_capacity 4000000 100 active
```

The canonical fixtures, identical probe source, copied binaries, command arrays,
per-process measurements and hashes are in
`training-output/lifetime-capacity-2026-09-11`. The probe enforces the ordinary
four-million-key resource envelope. Its cold-restore timer includes the first
state hash; the event timer excludes the final independent hash/conservation audit.
